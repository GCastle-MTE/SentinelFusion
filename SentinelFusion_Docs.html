00Overview & scope

A defensive network-security, threat-hunting, and OSINT desktop console.

SentinelFusion watches the traffic on your own machine and network in real time, attributes it to the processes and remote endpoints responsible, geolocates and enriches those endpoints against public intelligence sources, and raises plain-English alerts when it sees behaviour that matches known attack or exposure patterns. When related alerts add up, it correlates them into scored incidents, opens cases, and runs investigative playbooks automatically. It is built for monitoring, investigation, and response — it observes, detects, correlates, and recommends; it is not an attack tool and never executes containment on your behalf.

At a glance

  • Live packet capture with per-process and per-endpoint attribution
  • A detection engine spanning scans, floods, ARP spoofing, DNS tunnelling/DGA, beaconing, data exfiltration, malicious TLS fingerprints, and cleartext credentials
  • Process → connection mapping that classifies what each link is for (game server, voice, matchmaking, anti-cheat, CDN, telemetry)
  • One-click endpoint enrichment: geo, ASN, reputation, DNS history, flows, HTTP, link quality (RTT/jitter), passive OS and JARM fingerprints
  • Incident correlation with MITRE ATT&CK technique mapping
  • A SOAR layer: case management, trigger-based playbooks, and an audit run-log
  • 802.11 wireless IDS, proxy-chained OSINT, a live world map, and PCAP import/export
  • Case-based PDF reporting, SOC metrics (MTTA/MTTR, aging, trends), and a sensor health panel

Platform Windows, run as Administrator, with Npcap installed. Runtime Python 3.10 GUI Tkinter Capture scapy

Defensive use only. Everything here is for watching networks you own or are authorised to monitor. See Safety & ethics.

01Quick start

# From the project folder, in an Administrator terminal:
python app.py
  • Run as Administrator — packet capture needs it on Windows.
  • On first launch, open Settings → Capture interface and pick the adapter you want to watch (Wi-Fi, Ethernet, etc.), or leave it on Automatic.
  • Watch the top status strip and the Metrics tab fill in as traffic flows.
  • Anything suspicious lands in Alerts with an explanation, flags on the map, and — when related signals accumulate — rolls up into an Incident and a Case.
  • The ? button in the top strip opens an in-app guide to every tab.
To see detectors fire safely, generate traffic against your own devices — e.g. run a port scan from another machine you own, or open a plaintext FTP/HTTP-basic login. Never test against systems you don't control.

02The interface

A sticky status strip across the top shows live posture — capture state, endpoint and connection counts, flagged hosts, alert/warning tallies, packet rate, and an overall threat level (Normal / Guarded / Elevated). Everything else lives in sixteen tabs.

Metrics

The dashboard: a live throughput graph (bytes/sec over the last two minutes) plus top-level counters and the connection overview.

Applications

Traffic grouped by the local process responsible. Select a process and Map connections to see every endpoint it talks to, each classified by purpose. See Process → connection map.

Active

The live external endpoints your machine is currently exchanging packets with.

Connections

The active flow table — source/destination, ports, protocol, and volume per connection.

WiFi

802.11 wireless IDS (monitor mode) for deauth floods, rogue APs and evil twins, plus WiGLE OSINT. See Key features.

Network

A live inventory of every device on your LAN — IP, MAC, vendor, hostname, device type, passive OS guess, open ports, last seen. See Surveying your network.

Inspection

Deep packet inspection. Decode a packet's anatomy, follow its TCP stream, and import/export PCAP.

Alerts

Every detection, newest last, colour-coded by severity. Select a row for a plain-English explanation; right-click an IP to enrich, map, or export it.

Incidents

Related alerts about one actor, grouped and scored, with the ATT&CK techniques they map to. A whole attack chain becomes one incident. See Incident correlation.

Cases

SOAR case management — work an incident from new → investigating → contained → closed, with a note timeline, recommended actions, and one-click PDF report. See Cases & playbooks.

DNS

Every DNS lookup and what came back. Right-click a resolved IP to inspect it or trace its resolution chain. See The DNS log.

HTTP

Every cleartext HTTP request and response — method, URL, status, content-type, User-Agent. See HTTP transactions.

Flows

Every conversation as a session record — who, how long, how much each way, TCP state. See Session records.

Logs

The full event stream with a severity filter, pause, and a Retro-hunt search over stored history.

Watchlist

Rules you define — specific IPs/CIDRs, countries, or ASNs. Any match raises a watch alert.

Settings

Everything configurable, plus the operations console — health, detection rules, ATT&CK coverage, and config export/import. See Settings.

03Surveying your network

The Network tab answers "what is actually on my Wi-Fi, and what is it exposing?"

How devices are found

  • Active ARP sweep - "Scan network now" ARPs the whole subnet and lists everything that answers, with its MAC and vendor. A baseline sweep also runs a few seconds after launch.
  • Passive fingerprinting - devices constantly broadcast mDNS, SSDP/UPnP, DHCP and NetBIOS to the whole segment. Parsing that chatter identifies them (Chromecast, printer, router, Apple device...) without touching anyone's traffic.
  • Hostname resolution - reverse DNS usually fails on a home LAN, so each unnamed host is asked directly: a NetBIOS node-status query (what nbtstat -A sends - Windows answers with its computer name, workgroup and MAC), then a unicast mDNS reverse lookup (Apple / Linux / Android / IoT answer with their .local name).

Mapping what a host exposes

Select a device and hit Scan ports on selected. It runs a TCP-connect scan across common ports, identifies the service, grabs a banner where one is offered (so you get OpenSSH_8.9p1, not just "22 open"), and attaches a plain-English risk note to anything worth reviewing. Risky findings raise a service warning and mark the row with a warning symbol.

A port scan sends real traffic. On your own network this is routine asset auditing - the same thing you would do with nmap against your own kit. Keep it there: only scan hosts you own or are explicitly authorised to test.

LAN attack detection

  • rogue - the default gateway is trusted as the DHCP server at startup; any other server that starts answering raises an alert naming it, its MAC, and the gateway/DNS it is advertising. Catches both a DHCP-based man-in-the-middle and the honest accident of a spare router plugged in with DHCP still on.
  • arp - ARP spoofing / MITM, from an IP's MAC address changing.
  • device - a new device joining after the initial inventory has settled.
What this cannot do. An access point behaves like a switch: it only forwards your traffic to you, plus broadcasts. So you can inventory, fingerprint, name and port-scan every device - but you cannot passively read another device's traffic contents without a managed switch's mirror port or a network TAP. That is a hardware boundary, not a software one. (The alternative, ARP spoofing, is a man-in-the-middle attack and is deliberately not implemented here.)

04Process → connection map

Which servers is this game (or app) talking to, and what is each one for?

From the Applications tab, pick a process and choose Map connections. You get a visual with the process at the centre and every endpoint it talks to radiating out — each node coloured by its role. Click a node to see the evidence behind that verdict.

Roles it distinguishes

Game server, voice chat, matchmaking / platform API, anti-cheat, auth/login, CDN / content / update, telemetry / analytics, web / API, and peer-to-peer. The classifier weighs the resolved hostname and TLS SNI, ports, protocol, packet shape and rate, byte volume, ASN/ISP, and whether a flow looks like an RTP media stream — then explains its reasoning per endpoint.

The side panel also rolls the endpoints up by owning organisation (ASN/ISP) and flags the outliers worth a second look — a lone host that isn't a big known cloud, or an org appearing for the first time. Example, for a multiplayer game session:

game server · i3D.net· voice · Vivox (RTP)· matchmaking · AWS· anti-cheat · BattlEye· updates · Akamai

05Enriching an endpoint

Right-click any IP anywhere in the app and choose Enrich IP for a single dossier that assembles everything known about it, led by a headline risk verdict (HOSTILE / WATCH / NORMAL).

Who & where

Classification, resolved hostname, geolocation, ASN/ISP, and reputation-feed matches.

What it's done

DNS history, active flows with byte orientation, cleartext HTTP, and the correlated incident it belongs to.

Fingerprints

Passive OS guess (from the TCP SYN) and, on demand, an active JARM fingerprint of its TLS stack.

Link quality

Passive RTT (from the TCP handshake) and jitter (from real-time UDP) — how good the connection to it actually is.

The same menu offers DNS chain (why this connection exists — the lookup that led to it, or a flag if it was contacted with no DNS at all) and Export PCAP (dump the connection's retained packets to open in Wireshark).

06Reading the ops map

A live world map (on the Metrics view) of every remote endpoint your machine talks to.

What you're looking at

  • You sit at your geographic location; arcs reach out to each remote endpoint.
  • Each arc and node is coloured by the local process that owns the connection — the legend (top-right) lists them; click one to isolate just that process.
  • Moving dots travel along the arcs: amber = upload (you → remote), cyan = download (remote → you).
  • A red ring and “!” mark a flagged endpoint (an unacknowledged alert). Acknowledging its alert clears the flag.
  • Continents are drawn with a glowing cyan coastline against the dark ocean; the brighter lines are the equator and prime meridian.

Controls

  • Scroll to zoom (centred on the cursor).
  • Drag to pan the world — the HUD panels stay fixed.
  • On-canvas + / − / R buttons zoom in, out, and reset.
  • Hover an endpoint for a tooltip; it includes the flag reason if the node is flagged.

07TLS certificate inspection

JA3 fingerprints the client; the certificate is what the server claims to be.

Select a packet carrying a TLS handshake in the Inspection tab and the anatomy gains a TLS certificate section: subject, issuer, validity window, key type and size, signature algorithm, the SAN name list, and the serial. Anything wrong with it is listed underneath in red.

What gets flagged

FlagWhy it matters
hostname mismatchThe certificate is issued for names that don't include the host the client asked for. This is the classic signature of TLS interception.
self-signedNo certificate authority vouches for it. Normal for IoT and lab kit; suspicious for a public site.
expired / not yet validOutside its validity window - either neglected infrastructure or a clock/forgery problem.
weak keyRSA below 2048 bits.
weak signatureSigned with MD5 or SHA-1, both of which are broken.
long validityA leaf certificate valid far longer than a public CA would issue. (Suppressed for CA certificates, where long lifetimes are normal.)

Passive vs active

TLS 1.3 hides certificates from passive capture. In TLS 1.3 the Certificate message is encrypted, so watching the wire reveals nothing about it - that is the protocol working as designed. Passive inspection therefore only sees certificates on TLS 1.2 and below, which in practice is where most IoT, internal, and self-signed services live.

To inspect a modern server anyway, use the Network tab: scanning a host's ports performs a real TLS handshake against any TLS service it finds and retrieves the certificate that way. Because the app is the client, this works on TLS 1.3 too. Certificate problems found this way raise cert alerts.

On a LAN scan the app dials a host by IP, so a certificate issued for a hostname naturally won't match. That specific case is not flagged, to avoid a mismatch warning on every device you scan.

08Protocol classification (DPI)

A port number is a hint, not an answer. Real inspection asks what a stream is from its bytes.

Select a packet in the Inspection tab and the anatomy gains a Protocol classification section. Identification is by signature only - the port is never used to decide what something is, only to report whether it turned up somewhere unexpected. Around two dozen protocols are recognised, including HTTP, TLS, SSH, DNS, SMB, RDP, VNC, FTP, SMTP, IMAP, POP3, Telnet, MySQL, PostgreSQL, Redis, QUIC, WireGuard, BitTorrent, SIP, MQTT, SNMP, NTP and IRC.

Why this matters

SituationWhat you learn
SSH on port 443Raised as an protocol ALERT. Ports 53, 80, 443, 123 and 25 are nearly always allowed outbound, so a foreign protocol on one is the classic way to tunnel past a firewall.
SSH on port 2222A milder warning - either a service you forgot about, or something avoiding the standard port.
HTTP on 8080Nothing. 8080 is a recognised alternate HTTP port, so it isn't a mismatch.
High-entropy bytes on port 80No signature plus near-random data on a port that should be plaintext suggests an encrypted tunnel or custom C2.

Entropy, honestly

Entropy measures how random data looks - encrypted and compressed data approaches 8 bits/byte, plaintext sits near 4.4. But entropy is capped by sample size: 400 random bytes only reach ~7.46, because you can't fill 256 bins uniformly with 400 draws. A single fixed threshold would therefore silently miss every short encrypted payload, so the bar scales with payload length (measured against real random data at each size) and anything under 128 bytes isn't judged at all.

What is deliberately not identified: RTP. Its header is essentially two version bits and a payload-type range, which matches random data about 3% of the time - measured. Reliable RTP identification needs flow context (a stable SSRC, incrementing sequence numbers), so it belongs in flow-level classification rather than single-packet signatures. Reporting "unknown" is better than guessing.

09Reviewing a capture

Point the full inspection stack at a file instead of the wire.

The live engine inspects packets as they arrive. Import .pcap in the Inspection tab does the same work to a capture file and hands back a structured report: how many packets and conversations, which protocols are present, the busiest ports and top talkers, every DNS lookup and what it resolved to, the TLS certificates presented, any cleartext credentials, and a consolidated findings list. It opens automatically when a capture contains findings, and the Capture review button reopens it. Alerts and warnings are colour-coded in the report.

Completely isolated. Reviewing a file never writes to your live DNS log, endpoint table, map, or event bus - so opening someone else's capture, or a sample from the internet, can't contaminate what you're seeing from your own network. Findings are also judged from the packet timestamps in the file, not the wall clock.

The classic anomaly and port-scan detectors still run over an import as well, so scans and sweeps inside the file surface on the Alerts tab as before.

11Incident correlation

A real intrusion isn't one alert - it's a chain. This connects them.

Every detector fires independently, so a single attack scatters across the Alerts tab: a scan, then a new service, then beaconing, then a large upload - all involving the same host. The Incidents tab groups events that share an actor within a time window into one scored incident, and names the pattern when it recognises the classic kill-chain shape.

How scoring works

  • Each signal contributes by category weight and severity - exfil and beacon weigh heavily, device barely at all.
  • Breadth beats repetition. Four different detectors firing scores far higher than the same one firing forty times - because spanning multiple kill-chain stages (recon, access, evasion, C2, exfil) is what distinguishes a real intrusion from noise.
  • The result is banded into LOW / MEDIUM / HIGH / CRITICAL, and every incident carries the exact signals that built its score, so you can see why.

Select an incident to see its timeline and the detectors that fired; acknowledge it to clear it. The Rebuild from history button re-derives incidents from the stored event log - a lightweight retro-hunt over everything recorded so far. The Logs tab also has a full Retro-hunt search - filter the entire stored event history by text, category, severity or source IP.

12MITRE ATT&CK mapping

Every detector speaks the field's standard language.

Each detection category maps to the real MITRE ATT&CK technique(s) it represents. An incident's technique set is the union across the detectors that fired, de-duplicated and ordered by tactic — so a full intrusion reads as a recognisable progression rather than a pile of alerts:

T1046 · Discovery→ T1071 · Command & Control→ T1041 · Exfiltration

Technique IDs appear on the incident detail, are folded into the case summary, and are printed in the PDF report. Settings → ATT&CK coverage lists every technique the sensors can observe, grouped by tactic.

The mapping is deliberately limited to network-observable techniques the sensors can actually justify. A packet sensor can't see, say, Persistence or Privilege Escalation — so those tactics aren't claimed. Honest coverage beats an inflated matrix.

13The DNS log

DNS shows intent before the connection happens - a machine asks for a name, then talks to whatever came back.

The DNS tab logs both halves of every lookup: which host asked, what it asked for, the record type, the IPs that came back, the CNAME chain, and the TTL. Rows are colour-coded - amber for failed lookups, grey for a query still awaiting a reply, red when a resolved IP is currently flagged.

Why it earns its place

  • The reverse map. Every answered lookup teaches the app that an IP belongs to a domain, so a bare address elsewhere - in an endpoint dossier, on the ops map - gets labelled with the name it came from.
  • Bad resolutions. If a domain resolves to an IP on the reputation feeds, that raises an intel alert naming the domain - you catch it at lookup time, before the connection.
  • NXDOMAIN visibility. A burst of failed lookups is exactly how domain-generation-algorithm malware looks while it hunts for its command server. The Failed lookups only filter isolates them.
This is the same traffic dns_analyzer watches for tunneling and DGA detection - that module does the detecting, this one does the logging and the reverse map.

14HTTP transactions

For traffic that isn't encrypted, HTTP tells you almost everything.

The HTTP tab reconstructs every cleartext request and pairs it with its response: method, full URL, status code, content-type, and the request/response headers. Rows flagged as notable are amber; server errors are red. Filter by text, or show only flagged transactions.

Passive software inventory

The Software inventory button lists everything seen by its User-Agent (clients) and Server header (servers), with counts. This is a genuinely useful free by-product: outdated browsers, IoT firmware strings, and - flagged as TOOL - non-browser clients like curl, python-requests, powershell or scanners that usually shouldn't be talking to the internet.

What gets flagged

  • HTTP Basic-auth or a password/token in the URL - credentials crossing in the clear.
  • A download of an executable or script (.exe, .ps1, .apk...) over HTTP.
  • Automation/tooling User-Agents, and requests with no Host header.
Cleartext only, by definition - HTTPS is encrypted, so those requests appear as TLS in the protocol view instead. The HTTP analysis also runs over imported captures and is included in the capture review.

15Session / flow records

Individual packets are noise; the conversation is the signal.

The Flows tab groups packets into bidirectional sessions, keyed by the two endpoints regardless of direction. Each row is one conversation: the protocol (identified by deep inspection, not just the port), the endpoints with the remote hostname if DNS saw it, the TCP state, the duration, and - the useful part - the bytes sent in each direction. Sort by total bytes, bytes out, duration, packets, or most-recent, and optionally hide closed connections.

What the shape tells you

  • Big out, small in. A high out/in ratio is what a data upload looks like. Rows where a lot went out for little in reply are highlighted - worth knowing what they are and where they're going.
  • Long-lived, low-volume. A connection open for a long time carrying little traffic can be a tunnel or a remote-access session.
  • TCP state. A pile of half-open (syn_sent) flows is a sign of a scan or a SYN flood; reset flows are refused connections.
Flows expire after five minutes of silence and the table is capped, so long captures stay responsive. Flow accounting also runs over imported captures and appears in the capture review. This is also the context that lets protocols like RTP - which can't be identified from a single packet - be recognised reliably, since a flow exposes the stable endpoints and timing that a lone packet doesn't.

16Cases & playbooks (SOAR)

Security orchestration, automation & response — scoped to investigation.

When correlation produces an incident of medium severity or higher, SentinelFusion's SOAR layer goes to work automatically. It mirrors the three capabilities of a SOAR platform — case management, automation, and centralised intelligence — while staying firmly on the defensive side of the line.

Case management

An incident becomes a case you work through a lifecycle:

new→ investigating→ contained→ closed

Each case carries an assignee, a timestamped note timeline, the ATT&CK techniques involved, and a list of recommended actions. Everything persists to the database, so the record survives restarts.

Playbooks

A playbook is a trigger plus an ordered list of investigative actions. Triggers fire on incident shape — any incident, critical/high, suspected C2, credential exposure, data exfiltration — and run steps like: enrich the actor, trace the DNS resolution chain, capture PCAP evidence, hunt the same pattern on other hosts, open a case, tag its kill-chain stage, and attach recommended actions. Every action is read-only. The engine gathers, correlates, and recommends; it never changes a firewall rule or kills a process.

Recommended actions, applied by a human

Where containment is warranted the case says so in words — "review whether this IP should be blocked at the perimeter (analyst decision, not applied automatically)" — for a person to act on. That boundary is the whole point: automation as a force-multiplier, not an autopilot.

Run log

Every automated action is recorded with its result. The Run log (button on the Cases tab) is the audit trail — what fired, when, against whom, and what it found. An Auto-run playbooks toggle lets you work incidents by hand instead.

Investigative only. SOAR here never executes containment. It is an analyst's assistant that does the routine first steps and writes them down.

17Reports

From the Cases tab, Generate report produces a professional, case-centric PDF an analyst can attach to a ticket or hand to a manager. It gathers the case detail, the mapped ATT&CK techniques, the actor's enrichment profile, the full investigation timeline, the recommended actions, and the SOC metrics at time of writing — one self-contained document.

The older traffic-oriented report (incidents, devices, captures, alerts) is still available from the Inspection tab for a broad session summary.

18SOC metrics

Detection is half of operations; response is the other half. The SOC metrics window (Cases tab) reports the numbers a security lead watches:

  • MTTA / MTTR — mean time to acknowledge (first action on a case) and to resolve (open → closed).
  • Case aging — open cases bucketed by age (<1h / 1–24h / 1–7d / >7d), so nothing rots unnoticed.
  • Detection trend — events per day over the last week, with an inline bar chart and a by-severity breakdown.

All of it is derived from real case and event history, not synthetic counters.

19Detection rules & tuning

The detection engine isn't a black box.

Settings → Detection rules opens a catalog of every detector: what it fires on, the ATT&CK technique it maps to, and — where it has one — its live numeric threshold. Analysts can:

  • Tune a threshold (port-scan count, exfil volume, beacon intervals, deauth-flood count, correlation window). The change reflects onto the running engine immediately, on the next packet — no restart.
  • Enable or disable a rule. A disabled rule's whole category is suppressed at the source, so it stops generating events and stops feeding correlation.

The catalog is the single source of truth for what's watching and how sensitively.

20Health & self-check

A monitoring tool that quietly stops capturing is worse than none. Settings → Health watches the watcher and refreshes live:

  • Capture — packets/sec and liveness (is traffic still arriving?).
  • Buffers — in-memory footprint: endpoints, flows, DNS records, retained packets, event buffer.
  • Database — on-disk size of the incident store.
  • Subsystems — each module pinged and reported ok / error / absent.

It resolves to a single verdict — HEALTHY, DEGRADED, or NO TRAFFIC — so a stalled sensor is obvious at a glance.

22Key features

Alert triage / acknowledge

Acknowledge alerts you've reviewed — they dim, drop out of the HUD counters, and unflag their endpoint on the map. Filter with “Hide acknowledged”.

PDF report

From the Inspection tab, generate a report covering traffic summary, top endpoints (with ASN), a detections-and-alerts breakdown, and your watchlist.

CSV / JSON export

Export all alerts (with an acknowledged column) from the Alerts tab, for spreadsheets or a SIEM.

TLS certificate inspection

See who a server claims to be: subject, issuer, validity, key, signature and SAN list - with self-signed, expired, weak-key and hostname-mismatch flagged. Shows in the packet anatomy, and the Network tab fetches certificates from your own hosts directly.

Follow TCP stream

Reassemble a full TCP conversation from a selected packet, with direction colouring and an ASCII/hex toggle.

Capture review

Import a pcap and the whole inspection stack runs over it offline - protocol classification, DNS, TLS certificates, cleartext credentials and every finding - in a report that never touches your live monitoring state.

PCAP import / export

Load a capture file to inspect and replay the detectors over it (without touching live state), or save what you've captured.

Desktop notifications

A corner toast when a serious alert fires. Toggle it — and whether warnings count too — in Settings.

Offline GeoIP + ASN

With MaxMind GeoLite2 files present, endpoints are located and ASN-tagged offline; otherwise it falls back to an online lookup.

Tor / SOCKS routing

Optionally route outbound OSINT lookups through a proxy or Tor for privacy (your own capture stays local).

23Module reference

What each file in the project does.

Core

app.py

The main Tkinter GUI — all tabs, the HUD, theming, and wiring. Entry point: python app.py.

threat_detection.py

The capture engine. Aggregates packets per endpoint/flow, attributes processes, and runs the live checks.

events.py

The event bus — logging, the ring buffer + SQLite store, category explanations, and alert acknowledgment.

dpi.py

Deep packet inspection — decodes a packet into an ordered, human-readable anatomy, including TLS.

db_manager.py

SQLite / SQLAlchemy persistence for devices, captures, and events.

Detectors

anomaly_detectors.py

Ping sweeps, SYN floods, ARP spoofing, and DNS zone-transfer detection.

scan_detector.py

Port-scan detection (many ports from one source).

dns_analyzer.py

DNS tunneling (entropy of subdomains) and DGA (high-entropy non-resolving domains).

dns_log.py

Full DNS message parser and transaction log. Builds the IP → domain reverse map that names endpoints across the app.

cred_sniffer.py

Extracts cleartext credentials from plaintext protocols — passwords are masked.

os_fingerprint.py

Passive OS guess from a host's TCP SYN (initial TTL + window size + option ordering, p0f-style). Surfaces the device that isn't what it claims to be.

jarm_fingerprint.py

Active TLS server fingerprinting (JARM). Sends ten varied ClientHellos and hashes the responses - C2 servers built from the same tooling share a JARM even behind different domains and valid certs. On-demand only, from the enrichment panel.

wifi_wids.py

Passive 802.11 wireless IDS: detects deauth/disassoc floods, rogue APs (your SSID from an unexpected BSSID) and evil twins. Detection-only - never transmits. Needs a monitor-mode-capable adapter; stays dormant and labelled otherwise.

rtt_tracker.py

Passive link quality - RTT from the TCP handshake (SYN to SYN-ACK) and jitter from real-time UDP inter-arrival spread. Answers "which game/voice server is laggy" with no active probing.

dns_chain.py

DNS resolution chains: links a live flow back to the lookup that spawned it, and flags connections to IPs with no observed DNS query (hard-coded / cached / IP-literal C2).

infra_rollup.py

Groups every connection by owning organization / ASN, so clusters of known cloud stand apart from the lone outlier host worth a second look.

novelty.py

First-seen ledger for IPs, domains and JA3/JARM fingerprints, persisted to disk. Flags infrastructure appearing for the first time this session.

service_roles.py

Classifies what each of a process's connections is for - game server, voice chat, matchmaking/platform, anti-cheat, CDN, telemetry - from hostname, ports, packet shape, RTP detection and ASN, with the evidence behind every verdict. Drives the Applications tab's "Map connections" view.

enrichment.py

Parses external logs - syslog (RFC 3164/5424), Windows Event Log, and generic JSON/key-value lines - into one normalized record, classifies security-relevant events (auth failures, firewall denies, lockouts, Windows event IDs), and forwards them so external logs correlate alongside packet detections.

log_sources.py

The listeners behind log ingestion: a UDP syslog server, a growing-file tailer, and a Windows Event Log reader, each on a background thread feeding log_ingest.

Closes the loop: analysts mark detections true/false positive, and per-category precision drives honest, directional tuning recommendations against the detection-rules catalog. Nudges are applied only on explicit action.

25Safety & ethics

SentinelFusion is a defensive and investigative tool. To keep it that way:

  • Only capture on networks you own or are authorised to monitor.
  • Test detectors against your own devices — never scan or probe systems you don't control.
  • OSINT lookups query public databases (reputation feeds, GeoIP, WiGLE) about addresses; treat what you learn responsibly.
  • Captured passwords are always masked before they're shown or logged — the tool flags exposure, it doesn't hoard secrets.
  • WiFi features are detection and OSINT only; there is no attack tooling here.
This is a personal security-research project, provided as-is. It is not a substitute for a professionally managed IDS/IPS, and it can produce false positives — always corroborate an alert before acting on it.
